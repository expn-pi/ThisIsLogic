# Level design

The level format is in Game design, in `CLAUDE.md`. This file holds its details and reasons, and the alternatives rejected.

- Example, a home alarm. Statement: the alarm goes off if the motion, window and door sensors are all on; or if the motion and window sensors are on but the door sensor is off; or if the motion sensor is on but the window sensor is off. Starting formula: `( 1 AND 2 AND 3 ) OR ( 1 AND 2 AND NOT 3 ) OR ( 1 AND NOT 2 )`. Sentences: "Motion sensor on", "Window sensor on", "Door sensor on". Solution: `1`.
- Propositions are numbers in the formulas, and their sentences come in a list. Each sentence is written once, so a typo cannot silently create another proposition; formulas stay short and easy to check, even with long sentences or with statements whose conditions come from context; and, since numbers have no spaces, the analyzer can split a formula at its spaces. The list holds only the sentences, in order, since the position gives the number. Numbers start at 1, as a person counts; the analyzer turns each into an index from 0 (see `Docs/Logic.md`), from which the notation derives the letter (see `Docs/BlockCreation.md`).
- In a formula, the pieces are separated by spaces, and each operator has a single text: the words `TRUE`, `FALSE`, `NOT`, `AND`, `OR`, `XOR`, `NAND`, `NOR`, `THEN` and `IF`, and the symbols `=`, `(` and `)`. Uppercase words give the operators a single rule, with only `=` and the parentheses as symbols, and a formula reads close to its statement; the cost is longer formulas. `IF` is ← because `1 IF 2` says the same as `2 THEN 1`. With a single text per operator, the analyzer is a simple table, and every level is written the same way.
- A formula is read with the game's convention of precedence and grouping (see `Docs/Logic.md`), so the author needs parentheses only where the convention would read it otherwise, and may add more for clarity, as in the example above. A chain of `=` groups from the right: `1 = 2 = 3` is `1 = ( 2 = 3 )`, which is not "all three are equal".
- Level texts are ASCII only. The textbook symbols (∧, ↔...) appear only on the screen, through the notation: in the core's standard C++, a ∧ written in the code depends on how the compiler encodes text, and words are easier to type.
- Splitting at the spaces lets the analyzer read the formula piece by piece instead of character by character. A piece that is neither an operator text nor a proposition number is an error that stops the game: levels are written by their author, so an error is a typo to fix, not a case to handle. A forgotten space, as in `4)`, falls in this case instead of silently becoming proposition 4 without the parenthesis.
- The solution comes with the level, so the game does not compute the minimal form: the author knows the solution when writing the level. The solution must be as small as a formula equivalent to the starting one can be, in the game's size, its number of propositions and constants (see `Docs/Logic.md`), counting every operator of the game, since ⊕, ↔, ↑ and ↓ may need fewer propositions than ∧, ∨ and ¬. The game checks only that the starting formula and the solution are well formed and that the solution is equivalent to the starting formula, and, as with an unknown piece, a failed check stops the game (see `Docs/Exercise.md`); it takes the solution's size on trust. A solution larger than needed is a level bug that the game does not handle: a player who finds a smaller formula loses, since winning needs the solution's size (see `Docs/LevelResult.md`).
- The starting formula must be larger than the solution, or the level starts solved, and a Submit right away wins; the game does not check it. Since the ¬ and the parentheses are free in the size, a level whose simplification only removes them, such as a double negation or De Morgan's laws alone, would start solved, so every level must reduce the propositions.
- The statement is a whole sentence, shown to the player for the context: a question, such as whether the alarm goes off, followed by its condition. Only the condition becomes the formula; the question stays in the statement, so the formula has no result variable, and the solution of a level whose answer never depends on the propositions is a constant: ⊤ for always yes, ⊥ for always no. The statement may say the constants in words, as an answer ("...or else I don't go" for ⊥, "...not!" for `AND FALSE`). The sentences of the propositions are plain statements ("It rains"), with no "if": the "if" belongs to the statement, which links the question to the condition, and a sentence with "if" or with its own negation reads wrong under a ¬. Statements should sound like something a person would say; exercises whose structure cannot be said naturally are left out.
- The levels are written in `Data/Levels.csv`, one per row, and imported as the DataTable `DT_Levels`, whose rows are `FLevelRow`, with one field per part of the level. The file is the source, and `DT_Levels` is reimported after each change; the fields are `VisibleAnywhere`, read-only in the editor, since an edit made there would be lost at the next reimport.
- `Data/` sits at the repository root, outside `Content/`: as with the source files of other imported assets, `Content/` keeps only the imported asset, which remembers its source file for the reimport. The editor does not show `Data/`, so the file is edited outside it (in Rider, in the File System view).
- In the file, the first column is the row name, whatever its header, and the other headers match the fields of `FLevelRow`. A text with commas goes in quotes. `Sentences` uses Unreal's list format, each sentence in quotes: in a spreadsheet, the cell is `("Alarm on","Motion sensor on")`; in the raw file, the cell itself goes in quotes and the inner quotes are doubled: `"(""Alarm on"",""Motion sensor on"")"`.
- Row names are numbers in sequence, since levels are played only in the file's order. The game reads a level by its position in the table, not by its row name, so the numbers are only labels.
- Levels are saved only as their texts. What derives from them, such as the tokens, the trees and the check of the solution, is computed by the game when a level is played. With the minimal form out of the game (above), these computations are cheap, and `Levels.csv` stays the only source of each level.
- The quick test level (`FQuickTestLevel`, in `Gameplay/Level/`) is a level written in code: a starting formula and its solution, in the same text as the levels', and its sentences. It exists for the author's quick manual tests, such as trying a formula or long sentences without editing `Levels.csv` and reimporting `DT_Levels`, and it is not part of the design: it does not weigh in design decisions, and the rules for it are looser than for permanent code, such as automated tests. A quick test swaps, in the GameMode's `BeginPlay`, where the level is read, the level's starting formula, solution and sentences for its `GetFormula`, `GetSolution` and `GetSentences`, so all three come from the same source and reach the exercise, the formula and the proposition palette by the same paths as a level's; its formula and solution go through the analyzer and the checks like any others, so a change to its formula needs the matching solution, and a quick test covers the start, Restart, Undo and inserting. It keeps no state, so it is a static class. Nothing includes it otherwise, so the compiler checks it only when it is used; it gets secondary attention and is deleted if keeping it compatible with the rest gets hard. It uses engine types (`TArray`, `FString`), so it stays out of `Logic/`.
- Rejected: propositions written as sentences inside the formula, in brackets, such as `[John eats tofu]` (every repetition retyped the sentence, and long sentences made formulas hard to write and read), or, as alternatives to the brackets, marked by parentheses (which also group) or found by splitting at spaces (which sentences contain); short names instead of numbers, such as `alarm` and `door` (more readable formulas, but the list would need name → sentence pairs); letters given in order of first appearance through a level-wide table, sentence → letter (the number already gives the letter); numbers from 0 in the level texts (a person counts from 1, and the conversion happens once, in the analyzer); the question as a result variable inside the formula, as in `1 = ...` (the formula mixed the question with its condition, and a level whose answer is a constant had the lone result variable, or its negation, as the solution, so a player who stopped at `1 = TRUE` lost); a fixed frame for the result variable outside the row, `A =` at the start or `→ A` at the end, set by the notation so that each player could pick the form (too much detail for the game's purpose, since the notation already covers the differences in symbols); row names that describe the level, such as `Alarm` (they stay valid when the levels are reordered, which matters only for saved progress across updates of the game, a concern left out); computing the minimal form in the logic core (a high cost for what the level already brings); levels saved precomputed, with the tokens and other data derived from their texts (a second copy of each level, kept in step with `Levels.csv` by a tool to write and maintain, to save computations that are already cheap); `^` for AND in the level texts, as in some courses (`^` is XOR in C++ and C#); the formula as a list of pieces in the file, `("1","=","(",...)` (the import would split it, but every piece needs quotes, doubled in the raw file, which makes formulas hard to write and read); reading the formula character by character (texts such as `NAND` and numbers such as `12` need rules for more than one character); the aliases `&`, `|`, `~` and `->` (a mix of symbols and words, once `NAND`, `NOR` and `XOR` are words); the textbook symbols in the level texts (non-ASCII text in the core's code, and harder to type); more than one text per operator (a larger table, and levels written in different ways); the formula stub, `FFormulaStub`, which held the tokens of a fixed formula, written by hand in two parallel arrays, and skipped the analyzer (with the analyzer in place, skipping it no longer helps, and a formula in text is easier to write than the two arrays); the name stub for the quick test level (a stub stands in for a dependency inside a test, while this is a level for the author's manual tests, and QuickTest also sets it apart from the automated tests of 2.6); the quick test level swapped where the blocks are created rather than where the level is read (Undo and inserting would mix its formula with the level's sentences).
