# Logic core design

The core's rule is in Engineering principles, in `CLAUDE.md`: `Logic/` uses only standard C++, so it can be tested and reused on its own, with logging during development as the one exception. This file holds the details and reasons, and the alternatives rejected.

- The core reports an error by returning no result (`std::optional`, like a nullable type in C#), and its caller in the gameplay code decides what it means: in a level's formula, it is a typo of the level's author, and the caller stops the game with a `check` (see `Docs/Levels.md`); in the player's formula, a formula that is not well formed is a normal state, which the validity indicator shows. The core has no `check`, which belongs to the engine, and the standard `assert` is off in the Development Editor configuration.
- A table of literal data, such as the analyzer's operator texts or the parser's rules, pairs each key with its value (`{ "AND", ETokenKind::And }`) instead of using one array per field, as gameplay code does: with no `check`, the core could not confirm that two arrays have the same size, and with pairs there is nothing to confirm.
- The core uses C++20, the default in Unreal 5.8, such as designated initializers (`FToken Token = { .Kind = ETokenKind::And };`, like an object initializer in C#), defaulted comparisons (`FToken`'s `operator==` with `= default`, field by field, like a record's equality in C#) and `std::map::contains`.
- A token (`FToken`) is plain data: its kind (`ETokenKind`) and, for a proposition, its index in the level's list of sentences, from 0. The kind already tells which operator a token is, so only propositions need the second field. Operators keep the default index, -1, so an index read by mistake from an operator fails loudly at the list of sentences instead of silently giving the first one. One kind per concept; the texts of the levels belong to the analyzer.
- The token has no text: blocks take their texts from the notation and from the sentences (see `Docs/BlockCreation.md`). Nor does it say how its block is shown, such as whether it is minimized; that belongs to the block's state, in the gameplay code. Besides creating blocks, tokens are how the core sees a formula: the parser builds its tree from tokens, both for the level's formulas and for the player's formula, whose blocks keep their tokens (`AFormula::GetTokens` returns them in order), since the core cannot see the blocks.
- The analyzer (`FFormulaAnalyzer`) turns a level's formula into tokens; in compiler terms, this is lexical analysis. It is a static class, since it has no state and its table is fixed. It is the only place that turns a proposition's number into an index, and it returns no result at the first piece that is neither an operator text nor a number (see `Docs/Levels.md` for the format).
- An expression (`FExpression`) is a node of the tree together with everything below it, which is a sub-formula: its token and its operands, which are expressions too. One class serves every kind of node, since nodes differ only by their operator: leaves (propositions and constants) have no operands, ¬ has one, and the other operators two or more. The operands are kept by value, in a `std::vector`, which manages their memory, so copying an expression copies its whole tree, and `operator==` with `= default` compares two trees node by node. That is equality of structure, not equivalence: P ∧ Q and Q ∧ P are equivalent but not equal. Parentheses leave no node, since the shape of the tree already says what they said.
- The parser (`FFormulaParser`) turns tokens into a tree; in compiler terms, this is syntax analysis, which comes after the analyzer's lexical analysis. It returns no result when the tokens are not a well-formed formula, which is how validity is decided. It works by precedence climbing: a single method reads an expression and looks up each binary operator's precedence and grouping (`FOperatorRule`) in a table, so the convention is data, and another convention would change the table, not the code. ¬ stays out of the table: it applies only to the operand right after it, so it binds tightest under any convention. `Parse` is static and, inside, creates an object for that one parse, which keeps the tokens and the reading position, so the methods need not pass the position to each other (the Method Object pattern).
- A chain of one operator either becomes a single node with all its operands (`EGrouping::Flat`: Q ∧ R ∧ S is one ∧ with three operands, so the selection of 3.2 sees the three as siblings, and Q ∧ R is no sub-formula just for being on the left) or nests from the right (`EGrouping::Right`: P → Q → R is P → (Q → R)).
- The convention of precedence and grouping is the most common one in logic courses, with the gaps filled from the Wolfram Language (the language of Mathematica), which publishes the most complete table; where the two disagree, the courses win, since the game imitates their exercises. From the operator that binds tightest to the one that binds loosest:

| Order | Operator | Chain without parentheses | Source |
|---|---|---|---|
| 1 | ¬ | ¬¬P = ¬(¬P) | courses |
| 2 | ∧ | one node | courses |
| 3 | ↑ | one node: P ↑ Q ↑ R = ¬(P ∧ Q ∧ R) | Wolfram |
| 4 | ⊕ | one node | Aspnes, Wolfram |
| 5 | ∨ | one node | courses |
| 6 | ↓ | one node: P ↓ Q ↓ R = ¬(P ∨ Q ∨ R) | Wolfram |
| 7 | → and ← | from the right: P → Q → R = P → (Q → R) | courses; ← with →: ProofWiki |
| 8 | ↔ | from the right | courses |

- The sources disagree in places, which matters when writing a level or comparing it with a course. Some authors give ∧ and ∨ the same precedence and require parentheses between them. The place of ⊕ varies: some course notes put it between ∨ and →. The Wolfram Language makes ↔ bind tighter than →, and reads P ↔ Q ↔ R as "all equal", which differs from the grouping from the right: with all three false, "all equal" gives true, and P ↔ (Q ↔ R) gives false; since ↔ is written `=` in the levels, such a chain is easy to write by accident. Two choices have no convention behind them: ← shares the place and the grouping of →, and chains of ↑ and ↓ read as gates with several inputs, as in the Wolfram Language.
- Sources of the convention: [Stanford CS103, Propositional Logic](https://web.stanford.edu/class/archive/cs/cs103/cs103.1194/lectures/03-PropLogic/Propositional%20Logic.pdf); [Stanford Introduction to Logic, Operator Precedence](http://intrologic.stanford.edu/dictionary/operator_precedence.html); [Cornell CS486, FAQ](https://www.cs.cornell.edu/courses/cs486/2001SP/Assignments/faq.htm); [James Aspnes, Notes on Discrete Mathematics](https://www.cs.yale.edu/homes/aspnes/classes/202/notes.pdf); [Logical connective, Wikipedia](https://en.wikipedia.org/wiki/Logical_connective); [Binding Priority, ProofWiki](https://proofwiki.org/wiki/Definition:Precedence); [Operator Input Forms, Wolfram Language](https://reference.wolfram.com/language/tutorial/OperatorInputForms.html).
- The player may later choose the convention of their course (see Ideas in `CLAUDE.md`). A formula written for one convention may mean something else under another, so it is not read again with the new one: it is rewritten from its tree, with only the parentheses that the new convention needs around each operand (in compiler terms, pretty-printing, the reverse of parsing). The table then moves out of the parser, which receives it instead. The tree keeps no parentheses that the author wrote only for clarity, so a rewritten formula would lose them, unless each node marks that it came in parentheses.
- An expression evaluates itself (`Evaluate`) from one value per proposition index, which is a row of the truth table. Implications depend on the order of their operands; every other operator is decided by counting its true operands, which covers chains of any length and makes ¬ a ↓ with a single operand.
- Two expressions are equivalent (`IsEquivalentTo`) when they give the same value in every row of the truth table, built over the propositions up to the highest one that either uses; the comparison stops at the first row that differs, a counterexample. With the few propositions of a level, the table stays small.
- During development, the core logs with a `bIsDebug` flag in each method that logs (see Code style in `CLAUDE.md`). The parser's logs trace its reading, so the author can follow it through examples, and `IsEquivalentTo` logs the rows it compares; `Evaluate` logs nothing, since it runs for every node in every row and would flood the log. Token kinds are logged as numbers, in the order of `ETokenKind`.
- Rejected: an operator's kind stored as an integer, in the same field as a proposition's index (every use would convert it back, and an integer accepts values that are no kind at all); the token keeping its text, with the number read in its constructor (only the analyzer reads the text, and nothing else needs it); indices from 1 in the token (an offset of one in the notation and at the list of sentences); the analyzer as an object held by `AExercise` (it has no state); `assert` for the errors (off in the project's builds); one method per kind of piece and `std::from_chars` to read numbers (more code than the task needs: a check for digits and `std::stoi` are enough); a class per kind of node, under an abstract base, as in the Interpreter pattern (in C++, polymorphism works only through pointers, so the operands would be `std::unique_ptr`, which cannot be copied, copying a tree would need a `Clone` in each subclass, and most methods would be repeated in each subclass, while the nodes differ only by their operator); the tree as plain data, with static classes doing the work on it (the class that keeps the data does the work on it, by Tell, Don't Ask); one method per level of precedence (eight methods, with the order fixed in the code); parentheses required wherever the conventions disagree (a complete convention gives every formula a single reading, and the game only has to fix one).
