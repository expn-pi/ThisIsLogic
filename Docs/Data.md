# Data design

The rules are in Data rules, in `CLAUDE.md`. This file holds their details and reasons, and the alternatives rejected.

- Values stay in code even though changing one needs an editor restart: for the author, who works mostly in the IDE and uses the editor mostly to watch the game run, a restart is more practical than finding a field among the editor's many options.
- A class's own fields get their defaults where they are declared, as in C#. The constructor sets inherited fields (such as `bShowMouseCursor` in the player controller) and makes calls (such as `SetColor` in `APropositionBlock`), since a subclass cannot initialize a base class field at its declaration. `ABlock` shows how an owner configures its components through setters, with `Label` and `Background`.
- Editor assets that hold configuration pay off in three cases: many items of the same shape (levels, enemies, weapons), each in its own asset or table row; values tuned by eye (positions, sizes, colors, curves); and references between assets, which the editor keeps up to date when an asset is renamed or moved. For pure data, a Data Asset fits better than a data-only Blueprint; a Blueprint subclass pays off when the variation includes components, as with a prefab variant in Unity.
- This project has few such cases: the levels, kept in a `.csv` file and imported as a DataTable (reimported when the file changes), the UI layout, and possible visual adjustments to gameplay classes.
- A gameplay class may be a Blueprint subclass for visual adjustments, such as a position relative to another object. Each such value is set in the Blueprint or in C++, never in both: a default changed in C++ does not reach a value already adjusted in the Blueprint, and a value the C++ sets while the game runs overwrites the adjustment, both without warning. It is the same arrangement as the Widget Blueprint.
- UI widgets: the Widget Blueprint is edited in the UMG designer. The C++ class gets its widgets through `UPROPERTY(meta = (BindWidget))`, which stops the Widget Blueprint from compiling when one is missing, and binds their events itself (`OnClicked.AddDynamic`; the handlers are `UFUNCTION()` only for the reflection). Its own events to its owner use the usual single-listener delegates. No C++ method is `BlueprintCallable`: the code uses the asset, as with a serialized button and `AddListener` in Unity. The reasons against Blueprints barely apply here: the layout and look are meant to be edited visually, and the code sets none of those values, so nothing is silently overridden.
- A Blueprint class is an asset, so the C++ finds it only by its path, read from `UThisIsLogicSettings`. Creating the C++ class instead would leave out everything the Blueprint adds, such as the layout of a widget.
- Asset references: the paths in `Config/DefaultGame.ini` can be edited with the editor closed (or in Project Settings). Classes read them through `GetDefault<UThisIsLogicSettings>()`, outside constructors, since loading an asset in a constructor is risky. If a path breaks, the getter's `check` stops the game with an error at that getter.
- Moving or renaming an asset means updating its path in `DefaultGame.ini` by hand; Copy Reference in the Content Browser gives the path, between the single quotes. This is accepted, as with a hand-kept path manager for prefabs in Unity: a path is easy to find, while a Blueprint created only to hold a reference has to be opened and searched for the field.
- Since values stay in code, the settings hold only asset references: about ten by the end of the roadmap (the block material, the input assets, the Widget Blueprints of the panel and the menus, the levels' DataTable). One class with its fields grouped by `Category`, one section per area in Project Settings, is enough until it gets hard to read.
- Rejected: Blueprint subclasses for data the code can hold, including Blueprints created only to hold references (edited only in the editor, their saved values silently win over the code, and each class needs its own asset; visual adjustments are the exception, above); tuning values in the settings to change them without a restart (the author prefers restarting to looking for fields in the editor); one settings class per area from the start (more classes than about ten references need, and categories already group them); asset paths written in C++ (unusual in Unreal, and every change needs a rebuild); a central Data Asset (edited only with the editor open, and still found through a path); a hand-made singleton holding engine objects (the garbage collector does not see it); logic in a Widget Blueprint's graph, or C++ methods exposed to it with `BlueprintCallable` (the asset would call the code, like an OnClick wired in Unity's Inspector).
