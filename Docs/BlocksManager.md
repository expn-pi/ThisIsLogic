# Blocks manager design

- `AAbstractBlocksManager` is the abstract base (`UCLASS(Abstract)`) of the actors that hold blocks: the formula and the palettes. It keeps the blocks' board and factory, creates the blocks, registers their events and hands their organization to `FBlockBoard` (see `Docs/Layout.md`), so the formula and the palettes no longer repeat that code; each subclass decides what the blocks' gestures mean.
- The base has only what all its subclasses use (see Engineering principles in `CLAUDE.md`). For now, the board and the factory are private, and the base still forwards to the board requests that only the formula makes (inserting a block, at the end or before another, removing blocks, minimizing the propositions, giving the blocks' tokens and states and applying states, dragging and laying out the rows), which break that rule. In 1.24 they move to the board, which, as an object the subclasses contain rather than a base they inherit, may offer what only some of them use; the subclasses then reach the board directly, since all of them use it, and the factory goes into the board, so no subclass knows it.
- Creating a block, registering it (its engine `Owner` and its events) and handing it to the board happen in a single request, such as `CreateBlockBefore` for inserting before the selected block, and the part these requests share stays private: no block enters the board without its events, and no subclass ever holds a block that is not on the board.
- The base asks each subclass for what it decides through virtual methods (Template Method, as `GetText` in `ABlock`), such as the distance between rows in block heights (`GetRowHeightRatio`): 1.5 in the formula, which keeps its rows apart, and 1.1 in the palettes, which keeps the operator column compact. Every subclass must answer the tap, so the base gives it `unimplemented()`; moving and dropping are hooks, steps with a default behavior that a subclass replaces when it needs to: empty in the base and replaced only by the formula, since a palette's items stay in place. Registering a block is virtual too: the formula calls the base's through `Super` and then binds the propositions' own event, until the gestures change (1.25). The blocks' events are bound to the base's methods and still reach a subclass's override, since a pointer to a virtual method keeps the override, as a C# delegate made from a virtual method does.
- The blocks' height is a single constant of the base (`BlockHeight`, 2 cm; see `Docs/Scale.md`). The factory receives it in its constructor, which runs while the base is being constructed, when a virtual call does not reach the subclass yet (in C#, it would); and a palette item must look like the block it inserts, which one constant guarantees. Once the board's refactor (1.24) builds the factory later, the height can be asked of the subclass like the distance between rows.
- The rows' maximum width reaches the board through `SetMaxRowWidth`, which joins it with the height and the subclass's distance between rows in the board's `SetData`. It is public: the GameMode calls it on the formula, whose width belongs to the table's arrangement (see `Docs/Assembly.md`), and a palette calls it on itself with the width it computes from its blocks (see `Docs/Palette.md`).
- For now, the base keeps the propositions' sentences, since its factory uses them: the exercise gives them to the formula (`SetSentences`), and the proposition palette (1.26) will receive them the same way. The operator palette never uses them, so in 1.24 they go into the board with the factory.
- Names avoid C++ name hiding (see Code style in `CLAUDE.md`): the palette's virtual method that says which items it shows is `GetItemTokens`, apart from the base's `GetTokens`; the base's request to minimize or maximize the propositions is `SetPropositionsMinimized`, apart from the formula's command `SetAllMinimized`, which would otherwise call itself; and no subclass has a `CreateBlocks` or `RemoveAllBlocks` of its own.
- Planned (1.24): the board becomes a UObject that keeps the factory and the sentences, creates the blocks, registers their events and relays to the base the gestures whose meaning the subclasses decide; the casts to the concrete block classes and the requests that only some subclasses make move into it too (see `Docs/Layout.md`). The base then keeps only what every subclass uses: the board, the callbacks it registers on it and the decisions it asks of its subclasses.
- Rejected: `ABlockOwner` (in design discussions, the owner is the object that keeps another in a field, here the board; the actor is only the blocks' engine `Owner`); `ABlockArea` (it does not say what the class does); a board, a factory and a block height in each subclass (repeated code, and a palette item could drift from the block it inserts); the height asked of the subclass through a virtual method now (the factory is built during the base's construction); the maximum width asked through a virtual method (the formula's comes from the GameMode after the formula is created, so it would need a deferred spawn only to fit the pattern); the sentences passed to each request that creates blocks (the operator palette built an empty list, while whoever keeps the factory can keep them); separate requests to create a block and to place it (a block could be left off the board, outside the rows, where neither Restart nor Undo would destroy it).
