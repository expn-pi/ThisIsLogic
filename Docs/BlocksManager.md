# Blocks manager design

- `AAbstractBlocksManager` is the abstract base (`UCLASS(Abstract)`) of the actors that hold blocks: the formula and the palettes. It creates their board (`UBlockBoard`, the blocks' facade; see `Docs/Layout.md`) in its constructor, gives it its own position as the rows' origin and binds its events in `BeginPlay`, and passes it the rows' data through `SetMaxRowWidth`; each subclass decides what the blocks' requests mean.
- The base has only what all its subclasses use (see Engineering principles in `CLAUDE.md`): the board, the binding of its events, the rows' data and the decisions it asks of its subclasses. The board is a protected attribute, which the subclasses use directly for everything about their blocks, so the base has no requests of its own that only repeat the board's. A base may instead keep an attribute private and offer protected methods for it, so that its subclasses do not even know the attribute's class, as `ABlock` does with `SetColor` for its background; for the board, those methods would put in the base the requests that only the formula makes (inserting, removing, the blocks' states, dragging, minimizing), against the rule above, and would make the base a Middle Man (a class that only passes calls on).
- The base asks each subclass for what it decides through virtual methods (Template Method, as `GetText` in `ABlock`), such as the distance between rows in block heights (`GetRowHeightRatio`): 1.5 in the formula, which keeps its rows apart, and 1.1 in the palettes, which keeps the operator column compact. In `BeginPlay`, it binds the board's four events, once, to virtual methods: every subclass must answer the request to select, a tap, so the base gives it `unimplemented()`; moving, dropping and, until the gestures change (1.25), the propositions' request to minimize or maximize are hooks, steps with a default behavior that a subclass replaces when it needs to: empty in the base and replaced only by the formula, since a palette's items stay in place. The events are bound to the base's methods and still reach a subclass's override, since a pointer to a virtual method keeps the override, as a C# delegate made from a virtual method does.
- The events are bound in `BeginPlay`, the usual place in Unreal, rather than in the constructor, which also runs for the class default object. `BeginPlay` runs before any block exists: the formula's blocks come later, from the exercise's `BeginPlay`, and a palette creates its own right after calling the base's.
- The blocks' height is a single constant of the base (`BlockHeight`, 2 cm; see `Docs/Scale.md`), since a palette item must look like the block it inserts, which one constant guarantees. It reaches the board through `SetMaxRowWidth`, which joins it with the rows' maximum width and the subclass's distance between rows in the board's `SetData`. `SetMaxRowWidth` is public: the GameMode calls it on the formula, whose width belongs to the table's arrangement (see `Docs/Assembly.md`), and a palette calls it on itself with the width it computes from its blocks (see `Docs/Palette.md`).
- Requests from outside that concern only some subclasses live in those subclasses, which pass them to the board: the formula's `SetSentences`, called by the exercise, and `GetStates`, which the exercise asks for its Undo snapshots; the proposition palette (1.26) will have its own `SetSentences`. As public methods of the base, any class could call them on a subclass that has no use for them, such as asking the operator palette for its states.
- Rejected: `ABlockOwner` (in design discussions, the owner is the object that keeps another in a field, here the board; the actor is only the blocks' engine `Owner`); `ABlockArea` (it does not say what the class does); a protected getter for the board (the subclasses may use a protected attribute directly, and, with no method chaining, every use would need a temporary); each subclass holding its own board, with the base asking for it through a virtual method (it moved the attribute down with no need, since a subclass may use a protected attribute of its base, and repeated the board's creation in every subclass); the base creating and registering the blocks (creating, registering and placing a block were split between the base and the board, and the base bound the events of every block, which it now binds once on the board; see `Docs/Layout.md`); requests used only by the formula kept in the base, as public or protected methods (against the rule that a base has only what all its subclasses use, and a Middle Man over the board); the blocks' height asked of each subclass through a virtual method (a palette item could drift from the block it inserts); the maximum width asked through a virtual method (the formula's comes from the GameMode after the formula is created, so it would need a deferred spawn only to fit the pattern).
