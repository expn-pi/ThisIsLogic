# Palette design

- New blocks come from two palettes, always visible: the operators, the same in every level, and the level's propositions, which change with each level. Their items are blocks, like the formula's, and a tap on one inserts a block with the same token into the formula, before the selected block, or at the end with nothing selected (see `Docs/Commands.md`). A palette does not know the formula: it reports the token through an event, which the GameMode binds to the formula (see `Docs/Assembly.md`), and the formula asks its board to create the new block, whose factory gives it the blocks' height and, for a proposition, its sentence.
- The palettes are actors in the world, like the blocks, rather than UMG widgets, like the panel: they reuse the block classes, the factory and `UBlockBoard`, so each item is drawn like the block it inserts, with the same font, and the board lays the items out as it lays out the formula's rows (see `Docs/Layout.md`); presses reach them through the same routing as the formula's blocks (see `Docs/Input.md`). Instead of following the edges of the screen, each palette has a fixed place on the table, set by the GameMode and framed by the camera like the formula (see `Docs/Scale.md`).
- `APalette` is an abstract base (`UCLASS(Abstract)`, like `abstract` in C#: it can be neither created nor placed in a map), itself a subclass of `AAbstractBlocksManager`, which keeps the board, binds its events and gives every block the same height, so an item looks like the block it inserts (see `Docs/BlocksManager.md`). `APalette` decides the distance between its rows and what a tap on an item means, and each palette is a subclass that only says which items it shows (`GetItemTokens`) and how wide its rows are, through virtual methods (Template Method, like `GetText` in `ABlock`).
- The operators are the same in every level, so their list lives in `AOperatorPalette`, written as token kinds, as in `FFormulaStub`, where a typo does not compile. They come in pairs of related operators (∧ ∨, ↑ ↓, → ←, ↔ ⊕, ⊤ ⊥, ( )), with ¬ last.
- The operator palette is a column on the left of the table, like the toolbar of an image editor: the operators are short symbols, drawn as circles one block high, so the column is narrow and stays at hand. The column is the board's ordinary layout with rows one block wide, so each row holds one item; its rows are 1.1 block heights apart, closer than the formula's 1.5, so the column stays compact.
- The proposition palette (1.26) goes at the top of the table, laid out in rows like the formula, which grow downward: the sentences need width and have no length limit, so a side column of maximized propositions would leave the formula little room. Its items show the letter and the sentence ("P: Alarm on"), like the formula's maximized propositions; since they are proposition blocks too, the palette doubles as the level's legend with no code of its own. It holds the level's propositions, known when the level loads, and later the ones defined from sub-formulas (3.3): at most 11, P to Z, since the notation's letters start at P and its `check` stops the game past Z. It receives the level's sentences the same way as the formula (see `Docs/BlocksManager.md`).
- The board registers a palette's blocks and relays their requests to the base, as it does for the formula, and the base binds every one of the board's events, since an event with no listener stops the game at its `check` (see `Docs/BlocksManager.md`). A palette answers only the tap, by reporting the item's token; its items stay in place, so moves and drops fall to the base's empty hooks. Until the blocks only report their gestures and each subclass decides what they mean (1.25), starting a drag on an item, or a long press, counts as a tap, since the block turns it into a selection request.
- Rejected: UMG widgets for the palettes (the items would be buttons imitating the blocks; the symbols would need a second font asset, a runtime one made from the same TTF, since the blocks' font is offline (see `Docs/Font.md`); and dragging from a palette, if it ever leaves the Ideas, would start in a widget and end in the world, mixing two input systems in one gesture); the operators' list in `AExercise` or in the GameMode (it never changes, so it belongs to its palette, and the exercise deals only with the level's problem); the operators written as text and passed through the analyzer (a typo would show only with the game running, at the `check` after the analyzer, and the levels' texts belong to the analyzer, so the palette would go through `std::string` to reach what is already an enum); a New letter item (in a simplification, a letter that is not in the level never helps: it breaks the equivalence or only lengthens the formula, and it has no sentence; a new letter comes with its definition, from Define as proposition, 3.3); the proposition palette at the side (the sentences need width).
