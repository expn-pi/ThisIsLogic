# Class diagram design

- The class diagram exists in two forms. The README holds it in Mermaid, text that GitHub draws, kept up to date with the code: a change that adds, removes or renames classes, or changes how they connect, updates it too. `Images/ProjectClassDiagram.png` holds the same diagram drawn by the author in Visual Paradigm Community, and it may lag behind the code.
- Each form covers what the other cannot. In the text, every change shows in git as lines added or removed, in the same history as the code, and a review compares each line with the code. The drawing is the one meant to be read: GitHub lays the Mermaid text out by itself, and with this many classes its arrows grow long and cross, so it is hard to tell where each one ends, while in the drawing the author groups related classes and keeps the arrows short. It also shows what the text cannot: the kind of each class by its color (actor, other engine object, plain C++ class, interface, Blueprint), non-navigable ends (the X) and abstract classes in italics; the text marks only the interfaces, the abstract classes and the Blueprint, with annotations (`<<interface>>`, `<<abstract>>`, `<<Blueprint>>`). Drawing it by hand is also how the author reviews the structure: placing each class and each arrow means checking every link against the code.
- A readable class diagram lets a whole team understand a project at a high level, to divide the work and to bring in new developers. Since this repository is a portfolio, the drawing also shows that practice to recruiters, so the README shows it first in its class diagram section, with the Mermaid text below it.
- The paragraph above the image links to the image's history on GitHub and says that the drawing shows the code of the latest commit there, and that it may lag behind the Mermaid diagram, so a lagging image never passes for a current one. A redrawn image goes into a commit whose code it shows, usually together with that code, which keeps the statement true, so the paragraph changes only with the notation, such as a new color in its legend.
- The image is a PNG with a white background: a JPG blurs lines and text and makes a larger file, and on a transparent background the black lines disappear in GitHub's dark theme. The Visual Paradigm project file stays out of the repository: it is binary, and readers need only the image.
- `Images/` holds the pictures shown in the README, apart from `Docs/`, which holds design decisions.
- Notation: an association (solid arrow, `-->`) when a class keeps an object of the other in a field, by value or by pointer, since in UML a field and an association are the same thing, a property, in two notations; a dependency (dashed arrow, `..>`) when it only uses the other, through parameters, local variables, casts, static calls or a reference to the class rather than to an object (`TSubclassOf`, `TSoftClassPtr`, `StaticClass()`, like `typeof` in C#); inheritance (`--|>`); and interface implementation (`..|>`), dashed, although in C++ it is inheritance too. A delegate bound by the owner creates no link from the part to the owner, which the part does not know. A subclass has the associations of its base, since it inherits its fields, but each association is drawn once, from the class that declares the field: the formula and the palettes inherit the association of `AAbstractBlocksManager` with `UBlockBoard` and have no line of their own to it.
- The diagram shows only the project's own classes, leaving out plain data types used everywhere, such as `FToken` and `ETokenKind`. `FQuickTestLevel` appears with a dependency from the GameMode, where a quick test uses it, through lines kept commented out. A Blueprint appears only when its C++ base is abstract, since the Blueprint is then the class actually created: `WBP_CommandPanel`, under its asset's name rather than its generated class's (`WBP_CommandPanel_C`), inheriting from `UCommandPanel`, with no arrow from the classes that create it, since the code reaches it only through `UCommandPanel` and a path in the settings. Blueprint subclasses of concrete classes, such as `BP_ThisIsLogicGameMode`, are left out: their C++ classes already show how the classes connect.
- Rejected: only the image (git cannot show what changed in it, and it lags silently); only the Mermaid text (no control over the layout); the image in `Docs/` (what the code shows is not described there; see Maintaining this file, in `CLAUDE.md`); a JPG; the Visual Paradigm project file in the repository; a notice on the image only once it lags (someone would first have to notice); the paragraph naming the commit whose code the drawing shows (a commit's id cannot appear in its own content, so the image needed a later commit of its own, and the paragraph changed at every redraw); dropping the notice while the image is current and restoring it in the next commit (someone would have to remember); a line from each subclass to what it inherits from its base (a solid line declares a second association, as if the subclass had a field of its own, and a dashed one only repeats the dependency that the inherited association already implies); making `UCommandPanel` concrete to keep Blueprints out of the diagram (`Abstract` keeps a panel without its layout from being created); a stereotype for the Blueprint in the drawing (laborious in Visual Paradigm Community, and its own color says the same); every Blueprint in the diagram (those with a concrete C++ base add nothing to how the classes connect).
