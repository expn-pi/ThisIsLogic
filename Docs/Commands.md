# Command design

- Every command works with a single pointer: press, move and release, with one finger or the left mouse button. No hover, right click, modifier keys, wheel, multi-finger or timed gestures (double tap, long press), so the same commands serve mouse and touch and carry over to another engine. Keyboard shortcuts may come later as desktop extras, never as the only way to a command. The one exception is a long press on a proposition, a shortcut for the panel's Minimize/Maximize button; like keyboard shortcuts, it is an extra, never the only way to the command.
- A press released before the pointer moves past a small distance is a tap; moving past it starts a drag; holding still for half a second is a long press (see `Docs/Input.md`). A tap on a block selects it, and so does starting to drag it: the block the player works with is the selected one. A tap on the background clears the selection. A long press does what a tap does, so a slow tap still works; on a proposition, it also toggles between the sentence and the letter, through the same command as the panel's Minimize/Maximize button, which acts on the selected block.
- Besides the formula, the screen has a palette, always visible, that is the source of every new block (the operators, the level's propositions and New letter, which creates the next free letter), and a panel of buttons. Minimize all and Maximize all are always visible, since they act on the whole formula whatever is selected; Remove appears with any block selected, and Minimize/Maximize only with a proposition selected. Undo and Restart are always visible. Every command has a button or a palette item; dragging moves blocks and is a shortcut for inserting and removing.
- Inserting: a tap on a palette item inserts the block after the selected one, or at the end of the row with nothing selected; dragging a palette item inserts it where it is dropped.
- Removing: the Remove button, or dropping a block on the palette, which is highlighted while the block is over it. Dropping inside the formula's area moves the block (to any of its rows, if it has several); dropping anywhere else puts it back.
- No confirmations: every command can be undone (Memento pattern). After each command that changes the blocks, `AExercise` saves a snapshot of the formula in `FUndoHistory`: the states of its blocks, in order. A block's state (`FBlockState`) is its token and, for a proposition, whether it is minimized; each block takes and applies its own state (`GetState` and `ApplyState`), and a subclass adds what is its own. The history starts with the level's initial snapshot and skips one equal to the current, so a drag that leaves the order as it was adds no step. Undo drops the current snapshot and rebuilds the blocks from the previous one, through the same path as Restart, then applies their states. Saving after each command, rather than before, needs no moment when a drag starts. The formula reports each change through an event; emptying the formula and applying states, both parts of Restart and Undo, report nothing.
- Each command exists once, as a method of the class that owns the data; buttons and gestures only call it, so undo, logs and tests see a single path.
- Restart is a command of `AExercise`, which owns the level: it creates the blocks again from the level's starting tokens, through the same path as the start of the level and as Undo, so they cannot drift apart, and the formula stub of quick tests covers all three (see `Docs/BlockCreation.md`). As at the start, the propositions come back maximized. Restart can be undone like any other command.
- Planned, once the tree exists: tapping the selected block again widens the selection to the smallest sub-formula around it, then to the next one out. A selected sub-formula can become a new proposition (Define as proposition): it takes the next free letter, the legend shows its definition, and the indicators expand it before the truth table.
- Laws: first a legend of the laws, for reference only; later, only if play calls for it, the panel lists the laws that match the selected sub-formula, each with its result. A tap on the formula never applies a law directly.
- In Unreal, the panel is a UMG widget (see `Docs/Data.md`), and the palette is planned as actors in the world, like the blocks, implementing `IPointerTarget`, which reuses the input routing. Menus and the HUD are UMG too. Rejected for the palette: UMG (dragging from it into the world mixes two input systems in one gesture). Rejected for the panel: actors in the world (anchoring to the screen, layout, button states and text scaling, which UMG already has, would all have to be programmed); widgets built only in C++ (laborious, and unlike the usual way of using UMG); Slate directly (its declarative syntax is method chaining).
- The panel's buttons sit in a Horizontal Box, so a collapsed button leaves no gap; the spacing between buttons belongs to what hides, a button or a box, so it disappears with it. Undo and Restart, always visible, come first, outside the selection box; the space after each of them is always needed, so it belongs to the button. The buttons that need a selection sit in their own box, collapsed with nothing selected; Minimize/Maximize keeps its own condition, since an operator can be selected too. In that box Remove comes first, so Minimize/Maximize sits next to Minimize all and Maximize all, the commands of its family. When shown, the box is `SelfHitTestInvisible` rather than `Visible`, so it takes no clicks itself, not even in the gaps between its buttons, while its buttons still do.
- Rejected: icons or a context menu on the block (hidden commands, too small for a finger without covering the neighbors, and a context menu must repeat the main interface anyway); radial menus (no engine support, they compete with dragging on touch, and they pay off only with heavy repeated use); removing by dropping anywhere outside the row (accidental removals, as in the macOS Dock, and ambiguous with several rows); insert options only after a tap on empty space (blocks touch, so there is no empty space between them); a "+" button between each pair of blocks (many tiny targets); a Duplicate command (the palette already holds every operator and the level's propositions); confirmation dialogs (people confirm by habit); laws built into gestures, as in DragonBox (special cases, a tutorial for each gesture, and a conflict with reordering); a quick tap to minimize or maximize and a long press to select (selection underlies most commands, and a long press is hidden, slower and harder for some players); Minimize all and Maximize all only with nothing selected (they act on the whole formula whatever is selected); placing the panel's buttons freely on the Canvas Panel (positions kept by hand as buttons come and go); Minimize/Maximize before Remove in the selection box (it would sit apart from Minimize all and Maximize all); a proposition that minimizes or maximizes itself on a long press, without the formula (a second path to the command, apart from the one the panel's button uses); an undo state with only the tokens (the propositions came back maximized, undoing the player's minimizing); the minimized state inside the token (the token belongs to the logic core, which never sees how a block is shown); the block keeping its `FBlockState` as a field instead of building it on request (operators would carry a minimized state they never use, and a proposition would change data of its base class); saving the state before each command (a drag would need a moment when it starts).
