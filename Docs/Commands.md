# Command design

- Every command works with a single pointer: press, move and release, with one finger or the left mouse button. No hover, right click, modifier keys, wheel, multi-finger or timed gestures (double tap, long press), so the same commands serve mouse and touch and carry over to another engine. Keyboard shortcuts may come later as desktop extras, never as the only way to a command. The exceptions are two long presses, extras like keyboard shortcuts: on a proposition of the formula, a shortcut for the panel's Minimize/Maximize button, and on a palette item, a shortcut for inserting before the selected block, or at the end with nothing selected.
- A press released before the pointer moves past a small distance is a tap; moving past it starts a drag; holding still for half a second is a long press (see `Docs/Input.md`). In the formula, a tap on a block selects it, and so does starting to drag it: the block the player works with is the selected one. A tap on the background clears the selection. A long press on a block of the formula does what a tap does, so a slow tap still works; on a proposition, it also toggles between the sentence and the letter, through the same command as the panel's Minimize/Maximize button, which acts on the selected block. On a palette, a tap and a long press insert, and a drag does nothing, since a palette's items stay in place (see Inserting, below).
- Besides the formula, the screen has two palettes, always visible, which are the source of every new block: the operators and the level's propositions (see `Docs/Palette.md`). It also has a panel of buttons: Minimize all and Maximize all are always enabled, since they act on the whole formula whatever is selected; Remove is enabled with any block selected, and Minimize/Maximize only with a proposition selected. The latter shows only what it would do to the selected proposition, Minimize or Maximize, and keeps the last valid text while disabled, starting with Minimize, since the propositions start maximized; its text changes whenever the selected proposition's state changes, by the button, a long press, Minimize all or Maximize all. Restart and Undo are always enabled. Submit is enabled only while the formula is equivalent to the level's solution (see `Docs/LevelResult.md`). Every command has a button or a palette item; dragging only moves blocks within the formula, since inserting by dragging from a palette and removing by dropping on one are ideas, not scheduled.
- Inserting works like typing in a text editor, with the cursor right after the selected block: a tap on a palette item inserts a block with its token there, and the new block becomes the selected one, as the cursor moves past what is typed, so taps in a row come out in order: with X selected, tapping ( and then P gives X ( P, with P selected. With nothing selected, a tap inserts at the start of the formula and selects nothing, so taps in a row come out reversed there (P and then Q give Q P), and to go on after a new block, the player selects it. Taps alone reach every position: to insert after a block, select it; to insert at the start, clear the selection. A long press on a palette item is a shortcut that mirrors the tap: it inserts before the selected block, and the new block becomes the selected one here too. With nothing selected, it inserts at the end of the formula and again selects nothing, so long presses in a row keep their order there.
- Removing: the Remove button removes the selected block and selects the next one, like the Delete key of a text editor, so presses in a row remove forward; removing the last block leaves nothing selected. Followed by a long press, it replaces a block: with ∧ selected in P ∧ Q, Remove and a long press on ∨ give P ∨ Q. A dragged block is held inside the formula's area, so dropping it always moves it, to any of the formula's rows (see `Docs/Layout.md`).
- No confirmations: every command can be undone (Memento pattern), except the two that end an attempt at the level, Restart and Submit (see below and `Docs/LevelResult.md`). After each command that changes the blocks, `AExercise` saves a snapshot of the formula in `FUndoHistory`: the states of its blocks, in order. A block's state (`FBlockState`) is its token and, for a proposition, whether it is minimized; each block takes and applies its own state (`GetState` and `ApplyState`), and a subclass adds what is its own. The history starts with the level's initial snapshot and skips one equal to the current, so a drag that leaves the order as it was adds no step. Undo drops the current snapshot and rebuilds the blocks from the previous one, through the same path as Restart, then applies their states. Saving after each command, rather than before, needs no moment when a drag starts. The formula reports each change through an event; replacing all its blocks, which the start of the level, Restart and Undo do through `SetTokens` and `SetStates`, reports nothing.
- Each command exists once, as a method of the class that owns the data; buttons and gestures only call it, so undo, logs and tests see a single path.
- Restart is a command of `AExercise`, which keeps the level's starting tokens: it sends them to the formula, which creates the blocks again through the same path as the start of the level and as Undo, so they cannot drift apart, and the quick test level covers all three (see `Docs/Levels.md`). As at the start, the propositions come back maximized. Restart clears the undo history before saving the starting state, so it cannot be undone: it is what a defeat does, without the result screen, and after a defeat the result screen's OK leads to it, through the GameMode (see `Docs/LevelResult.md`). It stays next to Undo, and the author accepts that a mistaken tap on it loses the attempt.
- Planned, once the tree exists: tapping the selected block again widens the selection to the smallest sub-formula around it, then to the next one out. A selected sub-formula can become a new proposition (Define as proposition, 3.3): it takes the next free letter, replaces the sub-formula and joins the proposition palette with its definition, so it can be inserted elsewhere, and the indicators expand it before the truth table.
- Laws: first a legend of the laws, for reference only; later, only if play calls for it, the panel lists the laws that match the selected sub-formula, each with its result. A tap on the formula never applies a law directly.
- In Unreal, the panel is a UMG widget (see `Docs/Data.md`), and the palettes are actors in the world, like the blocks (see `Docs/Palette.md`). Menus and the HUD are UMG too. Rejected for the panel: actors in the world (anchoring to the screen, layout, button states and text scaling, which UMG already has, would all have to be programmed); widgets built only in C++ (laborious, and unlike the usual way of using UMG); Slate directly (its declarative syntax is method chaining).
- The panel's buttons sit in a row, in this order: Restart, Undo, Minimize all, Maximize all, Minimize/Maximize, Remove and, apart from them, Submit. The buttons that need a selection come after Maximize all, in a Horizontal Box of their own, disabled with nothing selected; Minimize/Maximize keeps its own condition, since an operator can be selected too. A disabled button keeps its place, so no button moves when the selection changes. In that box Minimize/Maximize comes first, next to Minimize all and Maximize all, the commands of its family. The box takes no clicks itself (it is `SelfHitTestInvisible`, Not Hit-Testable (Self Only) in the editor), not even in the gaps between its buttons, while its buttons do; a click in a gap, or on a disabled button, reaches the world (see `Docs/Input.md`). Submit comes last, at the right end of the row, apart from the others after a gap of at least 48 (its slot padding), since it ends the attempt, and an accidental tap on it costs the level's progress; like the others, it keeps its place when disabled, and its outline sets it apart (see `Docs/Visuals.md`).
- Rejected: icons or a context menu on the block (hidden commands, too small for a finger without covering the neighbors, and a context menu must repeat the main interface anyway); radial menus (no engine support, they compete with dragging on touch, and they pay off only with heavy repeated use); removing by dropping anywhere outside the row (accidental removals, as in the macOS Dock, and ambiguous with several rows); insert options only after a tap on empty space (blocks touch, so there is no empty space between them); a "+" button between each pair of blocks (many tiny targets); inserting before the selected block and keeping the selection where it was, the earlier rule (it did not work like typing in a text editor, which players already know, so it was less intuitive and less practical); Remove like the Backspace key, selecting the previous block, so that a tap after it fills the removed block's place (the author prefers the Delete key, and with it a long press does the same); selecting the new block also when nothing was selected (the author sees no need: a tap always inserts at the start, and the player selects a new block to go on after it); a pair of panel buttons to choose between inserting before and after (a mode the player must keep in mind, and two more buttons, when taps already reach every position); a Duplicate command (the palettes already hold every operator and the level's propositions); confirmation dialogs (people confirm by habit); laws built into gestures, as in DragonBox (special cases, a tutorial for each gesture, and a conflict with reordering); a quick tap to minimize or maximize and a long press to select (selection underlies most commands, and a long press is hidden, slower and harder for some players); Minimize all and Maximize all only with nothing selected (they act on the whole formula whatever is selected); placing the panel's buttons freely on the Canvas Panel (positions kept by hand); hiding the buttons that need a selection, by collapsing them (the buttons after them moved whenever the selection changed); Remove before Minimize/Maximize in the selection box (with the box after Maximize all, Minimize/Maximize would sit apart from Minimize all and Maximize all); a proposition that minimizes or maximizes itself on a long press, without the formula (a second path to the command, apart from the one the panel's button uses); an undo state with only the tokens (the propositions came back maximized, undoing the player's minimizing); the minimized state inside the token (the token belongs to the logic core, which never sees how a block is shown); the block keeping its `FBlockState` as a field instead of building it on request (operators would carry a minimized state they never use, and a proposition would change data of its base class); saving the state before each command (a drag would need a moment when it starts); Submit anchored to a corner of the Canvas Panel (a position kept by hand, like the free placement above, and its alignment with the row depended on other values); clearing the history on Submit, with Restart still undoable (the author prefers a Restart without undo, since a lost level ends in a Restart anyway); removing the Restart button, now that it does what a defeat does (the author kept it); Minimize/Maximize as the toggle button's fixed text (it does not say what the button will do); Minimize fixed on the toggle button while it is disabled (the last valid text is more coherent for the author); a fixed width for the toggle button, through a Size Box or the text's Min Desired Width, so that Remove does not move when the text changes (the author accepts the small shift, since Remove can still be pressed again and again); Submit placed only by its gap after the other buttons (it moved with their widths, while a slot that fills a fixed-width row keeps it at the row's end; see `Docs/Visuals.md`).
