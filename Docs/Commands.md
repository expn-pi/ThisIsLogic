# Command design

- Every command works with a single pointer: press, move and release, with one finger or the left mouse button. No hover, right click, modifier keys, wheel, multi-finger or timed gestures (double tap, long press), so the same commands serve mouse and touch and carry over to another engine. Keyboard shortcuts may come later as desktop extras, never as the only way to a command. The exceptions are two long presses, extras like keyboard shortcuts: on a proposition of the formula, a shortcut for the panel's Minimize/Maximize button, and on a palette item, a shortcut for inserting after the selected block, or at the start with nothing selected.
- A press released before the pointer moves past a small distance is a tap; moving past it starts a drag; holding still for half a second is a long press (see `Docs/Input.md`). In the formula, a tap on a block selects it, and so does starting to drag it: the block the player works with is the selected one. A tap on the background clears the selection. A long press on a block of the formula does what a tap does, so a slow tap still works; on a proposition, it also toggles between the sentence and the letter, through the same command as the panel's Minimize/Maximize button, which acts on the selected block. On a palette, a tap and a long press insert, and a drag does nothing, since a palette's items stay in place (see Inserting, below).
- Besides the formula, the screen has two palettes, always visible, which are the source of every new block: the operators and the level's propositions (see `Docs/Palette.md`). It also has a panel of buttons: Minimize all and Maximize all are always visible, since they act on the whole formula whatever is selected; Remove appears with any block selected, and Minimize/Maximize only with a proposition selected. Undo and Restart are always visible. Every command has a button or a palette item; dragging only moves blocks within the formula, since inserting by dragging from a palette and removing by dropping on one are ideas, not scheduled.
- Inserting: a tap on a palette item inserts a block with its token before the selected block, or at the end of the formula with nothing selected, and the selection stays where it was, like a text cursor right before the selected block: with X selected, tapping ( and then P gives ( P X. Taps alone reach every position: to insert before a block, select it; to insert at the end, clear the selection. A long press on a palette item is a shortcut that mirrors the tap: it inserts after the selected block, or, with nothing selected, at the start of the formula rather than at the end like a tap; the selection stays where it was here too. For a tap, inserting at the end with nothing selected, rather than at the start, is open to revision after play tests.
- Removing: the Remove button removes the selected block. A dragged block is held inside the formula's area, so dropping it always moves it, to any of the formula's rows (see `Docs/Layout.md`).
- No confirmations: every command can be undone (Memento pattern). After each command that changes the blocks, `AExercise` saves a snapshot of the formula in `FUndoHistory`: the states of its blocks, in order. A block's state (`FBlockState`) is its token and, for a proposition, whether it is minimized; each block takes and applies its own state (`GetState` and `ApplyState`), and a subclass adds what is its own. The history starts with the level's initial snapshot and skips one equal to the current, so a drag that leaves the order as it was adds no step. Undo drops the current snapshot and rebuilds the blocks from the previous one, through the same path as Restart, then applies their states. Saving after each command, rather than before, needs no moment when a drag starts. The formula reports each change through an event; replacing all its blocks, which the start of the level, Restart and Undo do through `SetTokens` and `SetStates`, reports nothing.
- Each command exists once, as a method of the class that owns the data; buttons and gestures only call it, so undo, logs and tests see a single path.
- Restart is a command of `AExercise`, which owns the level: it sends the level's starting tokens to the formula, which creates the blocks again through the same path as the start of the level and as Undo, so they cannot drift apart, and the formula stub of quick tests covers all three (see `Docs/BlockCreation.md`). As at the start, the propositions come back maximized. Restart can be undone like any other command.
- Planned, once the tree exists: tapping the selected block again widens the selection to the smallest sub-formula around it, then to the next one out. A selected sub-formula can become a new proposition (Define as proposition, 3.3): it takes the next free letter, replaces the sub-formula and joins the proposition palette with its definition, so it can be inserted elsewhere, and the indicators expand it before the truth table.
- Laws: first a legend of the laws, for reference only; later, only if play calls for it, the panel lists the laws that match the selected sub-formula, each with its result. A tap on the formula never applies a law directly.
- In Unreal, the panel is a UMG widget (see `Docs/Data.md`), and the palettes are actors in the world, like the blocks (see `Docs/Palette.md`). Menus and the HUD are UMG too. Rejected for the panel: actors in the world (anchoring to the screen, layout, button states and text scaling, which UMG already has, would all have to be programmed); widgets built only in C++ (laborious, and unlike the usual way of using UMG); Slate directly (its declarative syntax is method chaining).
- The panel's buttons sit in a Horizontal Box, so a collapsed button leaves no gap; the spacing between buttons belongs to what hides, a button or a box, so it disappears with it. Undo and Restart, always visible, come first, outside the selection box; the space after each of them is always needed, so it belongs to the button. The buttons that need a selection sit in their own box, collapsed with nothing selected; Minimize/Maximize keeps its own condition, since an operator can be selected too. In that box Remove comes first, so Minimize/Maximize sits next to Minimize all and Maximize all, the commands of its family. When shown, the box is `SelfHitTestInvisible` rather than `Visible`, so it takes no clicks itself, not even in the gaps between its buttons, while its buttons still do.
- Rejected: icons or a context menu on the block (hidden commands, too small for a finger without covering the neighbors, and a context menu must repeat the main interface anyway); radial menus (no engine support, they compete with dragging on touch, and they pay off only with heavy repeated use); removing by dropping anywhere outside the row (accidental removals, as in the macOS Dock, and ambiguous with several rows); insert options only after a tap on empty space (blocks touch, so there is no empty space between them); a "+" button between each pair of blocks (many tiny targets); inserting after the selected block (taps in a row come out reversed unless the selection moves to each new block, and the start of the formula is reached only by dragging); inserting at the start with nothing selected (the end would be reached only by a long press, a shortcut, or by inserting and then dragging); a pair of panel buttons to choose between inserting before and after (a mode the player must keep in mind, and two more buttons, when taps already reach every position); a Duplicate command (the palettes already hold every operator and the level's propositions); confirmation dialogs (people confirm by habit); laws built into gestures, as in DragonBox (special cases, a tutorial for each gesture, and a conflict with reordering); a quick tap to minimize or maximize and a long press to select (selection underlies most commands, and a long press is hidden, slower and harder for some players); Minimize all and Maximize all only with nothing selected (they act on the whole formula whatever is selected); placing the panel's buttons freely on the Canvas Panel (positions kept by hand as buttons come and go); Minimize/Maximize before Remove in the selection box (it would sit apart from Minimize all and Maximize all); a proposition that minimizes or maximizes itself on a long press, without the formula (a second path to the command, apart from the one the panel's button uses); an undo state with only the tokens (the propositions came back maximized, undoing the player's minimizing); the minimized state inside the token (the token belongs to the logic core, which never sees how a block is shown); the block keeping its `FBlockState` as a field instead of building it on request (operators would carry a minimized state they never use, and a proposition would change data of its base class); saving the state before each command (a drag would need a moment when it starts).
