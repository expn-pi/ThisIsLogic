# Assembly design

- The GameMode (`AThisIsLogicGameMode`) assembles the table as the Composition Root, a term from dependency injection for the single place where the program's pieces are created and connected, once, at the start: it reads the level, creates the pieces, decides where they go and connects their events. After that, it only handles the result screen's OK, which it binds to itself: a Restart of the exercise after a defeat, the next level after a victory (see `Docs/LevelResult.md`); moving between maps is the GameMode's original role in Unreal. Unreal's GameMode already sets the game's rules and default classes (such as the camera pawn), so assembling the table extends its role with no new class. Every other class stays independent: it receives what it needs and never looks for it. As the one place that assembles everything, the GameMode is where knowing the pieces' concrete classes is acceptable, but nothing requires it to: it may also get pieces from a factory and handle them through an abstraction, a choice made case by case by weighing what the factory hides against what it costs (see the palettes' factory among the rejected alternatives).
- The GameMode reads the level, since reading the configuration and handing each piece its part is the Composition Root's work. It first reads the level's index from the travel options, in its `OptionsString`, which the engine fills before `BeginPlay`; on the first run there is no option, and the index is 0. `ReadLevelRow` takes the row at that index in the levels' table, which it gets from `UThisIsLogicSettings`, and returns a copy of it rather than the pointer that `FindRow` returns: that pointer points into the asset, which the engine may unload once nothing holds it, and the soft reference in the settings does not hold it. The name says Read and Row because, in Unreal, a level is also a map, and `LoadLevel` would suggest loading one. The GameMode keeps the index in a field, to tell the result screen whether this is the last level and to open the next one. It hands the starting formula and the solution, as texts, to the exercise, which analyzes and checks them (see `Docs/Exercise.md`), and the sentences to the formula and the proposition palette, which show the propositions. For quick tests, the three can be swapped in its `BeginPlay` for those of the quick test level (see `Docs/Levels.md`).
- In its `BeginPlay`, in this order, it reads the level and creates: the formula, near the table's origin, with the rows' maximum width and the level's sentences; the background target, below the blocks, whose tap goes straight to the formula's `ClearSelection`; the exercise, spawned deferred at its place, above the right end of the formula, kept in a field of the GameMode, and given the formula, the level's two texts and its indicators' assets, which the GameMode reads from the settings (the blocks' material and font and `M_Text`; see `Docs/Indicators.md`), through `SetFormula`, `SetFormulasTexts` and `SetIndicatorsAssets`; the panel, connected to the formula and the exercise; the result screen, connected to the exercise and to the GameMode itself, told whether this is the last level, and placed above the panel in the viewport (Z-order 1, against the panel's 0), so that it covers it (see `Docs/LevelResult.md`); then it calls the exercise's `FinishSpawning`, which runs its `BeginPlay`; the operator palette, whose two insert events go straight to the formula's `InsertBlock` and `InsertBlockAfter`; and last the proposition palette, spawned deferred and given the sentences and the same two insert events before its `FinishSpawning`.
- The exercise is spawned deferred so that, when its `BeginPlay` runs, it already has its formula and its starting tokens, and its indicators have their assets, which their own `BeginPlay`, run inside the exercise's, needs to build their meshes and lay out their labels (setter injection, since actors take no constructor parameters); and so that the panel can be connected in between: the panel needs the exercise for Restart, Undo and Submit, and the exercise, as it starts, empties and fills the formula, which sends the selection event the panel listens to, and checks the formula, which sends the equivalence event that enables the panel's Submit. The proposition palette is spawned deferred because its `BeginPlay` creates its items, one per sentence, so it needs the sentences first. `FinishSpawning` must get the same transform as the spawn, since a different one moves the actor to it; the exercise's place holds its indicators, so one method, `GetExerciseTransform`, gives the same transform to both calls.
- Each event is bound straight to the class that does the work: the panel's Minimize all, Maximize all, Minimize/Maximize and Remove go to the formula, Restart, Undo and Submit to the exercise, the background's tap to the formula, the palettes' insert events to the formula, the formula's selection event and the exercise's equivalence event to the panel, and the exercise's submission event to the result screen. The result screen's OK, which carries the result, goes to the GameMode, which decides between the exercise's Restart and the next level, so it keeps the exercise in a field; the author preferred this single event to two. The formula's change event goes to the exercise, which binds it itself, since it saves the snapshots for Undo. No other class relays an event it does nothing with.
- The formula's selection event carries two values: whether a block is selected and whether it is a proposition. The panel enables or disables its buttons from them and needs no reference to the formula, just as the exercise's equivalence event, with a single value, enables Submit with no reference to the exercise; either reference would also close an include cycle, since `Formula.h` includes `AbstractBlocksManager.h`, which includes `BlockBoard.h`, which includes `ThisIsLogicSettings.h`, which includes `CommandPanel.h`, and `Exercise.h` includes `Formula.h`.
- The selection event sends one notification per change, once the state is final (`SelectBlock` unmarks the previous block through `DeselectBlock`, which does not notify). It may also come when nothing changed (tapping the selected block, or the background with nothing selected), which is harmless, since the panel only shows what it receives.
- Positions and areas on the table (the formula's place and its rows' width, the palettes' places, the exercise's place, which holds its indicators, and the background target's depth) belong to the GameMode, since they describe the table as a whole; each piece decides only its own inner sizes, such as its blocks' height, a palette's width or the indicators' layout (see `Docs/Scale.md`). The GameMode does not create the indicators: they are a component of the exercise, at the exercise's place, so the exercise creates them without deciding any position on the table (see `Docs/Indicators.md`).
- Rejected: the exercise creating the formula, the background and the panel (it would decide positions, and the palettes, which need the formula, would have to get it from the exercise or be known by it, making it the center of everything again); a level manager that controls the exercise and passes it the palettes' decisions (a center that keeps acting after the setup); hand-made singletons holding the pieces (the garbage collector does not see them, and Play in Editor may run several worlds at once); subsystems used to look the pieces up (a Service Locator: each class hides what it depends on, while the GameMode shows every connection in one place); the panel asking the formula for the selection (the include cycle above, and a UI class depending on a gameplay class); the selection event carrying the selected block (its listener would keep a copy of the selection); `SelectBlock` calling a notifying `ClearSelection` (switching blocks would send two notifications, the first with nothing selected); the exercise placed in the `Main` map (it needs its formula before its `BeginPlay`, which only the GameMode, creating both, can give); the exercise reading the levels' table itself (a piece looking for its configuration instead of receiving it, with an arrow from the exercise to the settings); the exercise announcing the sentences through an event, for the GameMode to pass them on to the proposition palette (the GameMode decides when the exercise starts, so it needs no notice), or offering them through a getter (unneeded once the GameMode reads the level); the exercise handing the sentences to the formula (it did nothing else with them, and they only serve to show the propositions, which is the blocks' level); the exercise receiving the whole level row (it uses only the starting formula and the solution, which come as texts through a single setter); the GameMode analyzing the starting formula, itself or through a static helper class, and giving the exercise the tokens (the exercise would stop being the only class that calls the logic core, which keeps the conversions between engine types and standard types in one place, and the GameMode would call the logic core while creating actors, a mix that `Docs/BlockCreation.md` also rejects); a factory of the palettes, with one creation method per palette, each returning an `APalette` (the GameMode would trade the two concrete classes for the factory and the abstraction, a modest gain, and with 3.3 the proposition palette will have requests of its own, which the GameMode will connect, so it would need the concrete class again; nothing calls for it now); a private method of the GameMode that binds a palette's two insert events, taking an `APalette` (it removes a repetition of two calls, at the cost of an explicit dependency of the GameMode on one more class).
