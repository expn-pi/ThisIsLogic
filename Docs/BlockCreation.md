# Block creation design

- Data flow: level texts (DataTable) → analyzer → tokens → factory → blocks → formula, driven by `AExercise`. The analyzer and the tokens belong to the logic core (see `Docs/Logic.md`). `AExercise::AnalyzeFormula` is the bridge: it converts the formula's text to standard C++, calls the analyzer, checks for an error and copies the tokens into a `TArray`, so the factory and the rest of the gameplay code work only with engine types.
- `FFormulaStub`, in `Gameplay/Level/`, holds the tokens of a fixed formula, written by hand, and its sentences. A quick test, in `AExercise::CreateBlocks`, swaps the call to `AnalyzeFormula` for its `GetTokens` and the level's sentences for its `GetSentences`, so the tokens and the sentences always come from the same source, and the analyzer is skipped. Nothing includes it otherwise, so the compiler checks it only when it is used; it gets secondary attention and is deleted if keeping it compatible with the rest gets hard. It uses engine types (`TArray`, `FString`), so it stays out of `Logic/`.
- The factory is the only place that knows which block class to create (Simple Factory); `AFormula` knows only `ABlock`. Actors cannot take constructor parameters (the engine calls the default constructor, also for the class default object), so the factory uses a deferred spawn to fill in a block before `OnConstruction`.
- The factory is an object held by `AExercise`, built with the notation's first letter and the blocks' height (see `Docs/Scale.md`), and it owns the notation, its only user so far. During the deferred spawn it gives each block its height and then its text data. `CreateBlocks` turns all the tokens into blocks, so `AExercise` has no loop; `CreateBlock`, for one token, stays public, since the palette will create one block at a time. A proposition block gets the letter of its index and the sentence at that index in the level's list; an operator block gets the notation's text for its kind.
- `ABlock` is abstract and asks each subclass for its text (`GetText`): the subclass decides which text and when, and the base knows how to show it (label, width, background and owner notification). `APropositionBlock` keeps its letter and its sentence, set together by `SetProposition`, and whether it is minimized; `AOperatorBlock` keeps its symbol. The level's sentences, with the notation's letters, can also feed a legend like the "Define:" lists of textbook exercises.
- The notation (`FNotation`) holds what the player sees, and the levels never depend on it. The letters are a run of consecutive letters from a given first one: index N gets the letter N places after the first, with a `check` that the result is still a letter. Operator texts are kept by kind. For now they are ASCII, since the default font of `UTextRenderComponent` probably holds only Western European characters, and the textbook symbols (∧, ∨, ↔...) would show as squares; they need a distance field font made in the editor with those characters listed in Chars (a forum report says importing a Unicode Range of arrows froze the 5.2 editor).
- The notation lives in `Gameplay/Notation/`, not in `Logic/`: it uses engine types, and the core never needs it, since validity and equivalence do not depend on how a formula is shown. The analyzer has its own notation, the fixed one levels are written in (see `Docs/Levels.md`). The name is the logic term for how formulas are written; in Unreal, "Style" names the look of widgets (`FButtonStyle`).
- Shared types are grouped by domain (`Logic/LogicTypes.h`), not by kind of type.
- Rejected: global `Structs`/`Enumerators` files in a `SharedData` folder (unrelated types side by side, included everywhere); a factory holding block classes set in the Details panel (Blueprint subclasses that only held the material; see `Docs/Data.md`); text handling moved down to the subclasses (it would open `Label` and `Background` to them, or duplicate them in each); the base keeping the text, with one method to store it before construction and another to show it later (two paths for the same text); a `SetText` overridden in `APropositionBlock` (it was not virtual, and the name would lie, since the block may show the letter); one appearance method shared by `OnConstruction` and the subclasses that also notifies the owner (during construction the block has no owner yet); separate setters for the letter and the sentence (both always come together, once, at creation, so one method plays the part of the constructor an actor cannot have); a list of letters in each notation (computing them makes a notation just its first letter, at the cost of allowing only runs of consecutive letters); the notation in `AExercise`, which would get the letter or the text before calling the factory (it would repeat the factory's decision of which block gets which); the notation passed to a static factory on every call (it crossed every signature); `T` and `F` for the constants (`T` is also a letter) and `^` for XOR (many read it as AND); the factory reading a proposition's number from a token's text (two classes would know the level format); a single call in `AExercise` that analyzes and creates the blocks (it would hide the tokens of the starting formula, which the equivalence indicator needs); the factory taking the analyzer's `std::vector` (standard types would spread into the gameplay code, while the bridge converts them once); one class that takes the level row and does everything, from the text to the blocks (it would mix the logic core with the creation of actors); the stub creating its blocks itself (a second copy of the factory, to keep up with every change to the blocks); a stub that returns a level row (the stub stands in for the analyzer, not for the table).
