# Block creation design

- Data flow: level texts (DataTable) → analyzer → tokens → formula → board → factory → blocks. The analyzer and the tokens belong to the logic core (see `Docs/Logic.md`). `AExercise` stops at the tokens, the problem's level, and sends them to the formula, which asks its board to create the blocks with the factory the board keeps (see the two levels of abstraction in the Engineering principles of `CLAUDE.md`, and `Docs/Layout.md`); a palette creates its blocks the same way, from tokens of its own (see `Docs/Palette.md`). `AExercise::AnalyzeFormula` is the bridge: it converts the formula's text to standard C++, calls the analyzer, checks for an error and copies the tokens into a `TArray`, so the factory and the rest of the gameplay code work only with engine types.
- `FFormulaStub`, in `Gameplay/Level/`, holds the tokens of a fixed formula, written by hand, and its sentences. A quick test, in `AExercise::LoadFormula`, swaps the call to `AnalyzeFormula` for its `GetTokens` and the level's sentences for its `GetSentences`, so the tokens and the sentences always come from the same source, and the analyzer is skipped. The exercise keeps the tokens for the start of the level and Restart, and the sentences stay with the formula's board, for every block its factory creates, so a quick test covers the start, Restart, Undo and inserting. Nothing includes it otherwise, so the compiler checks it only when it is used; it gets secondary attention and is deleted if keeping it compatible with the rest gets hard. It uses engine types (`TArray`, `FString`), so it stays out of `Logic/`.
- The factory is the only place that decides which block class to create (Simple Factory); everyone else, the manager and its subclasses included, receives the blocks as `ABlock`, and besides the factory only the board may know the concrete block classes (see Engineering principles in `CLAUDE.md`). Actors cannot take constructor parameters (the engine calls the default constructor, also for the class default object), so the factory uses a deferred spawn to fill in a block before `OnConstruction`.
- `UBlockBoard` holds the factory and the sentences, so each formula and each palette has its own (see `Docs/Layout.md`). The factory is built only with the blocks' height, a single constant of the manager (see `Docs/Scale.md` and `Docs/BlocksManager.md`), once the board receives it through `SetData`: the board keeps it in a `TOptional`, a value that may not exist yet, like `T?` in C#, so using it before that stops the game at a `check`. The factory owns the notation, its only user so far. During the deferred spawn it gives each block its height and its token, together through `SetData`, and then its text data. Its `CreateBlocks` turns all the tokens into blocks, so its caller has no loop, and its `CreateBlock` creates one; the board's requests that create blocks use them and also register and place the blocks (see `Docs/Layout.md`). A proposition block gets the letter of its index and the sentence at that index in the list it receives (the sentences the board keeps: in the formula, the level's); an operator block gets the notation's text for its kind.
- `ABlock` is abstract and asks each subclass for its text (`GetText`): the subclass decides which text and when, and the base knows how to show it (label, width, background and the notice of its new width to its listener). `APropositionBlock` keeps its letter and its sentence, set together by `SetProposition`, and whether it is minimized; `AOperatorBlock` keeps its symbol. The proposition palette shows the level's propositions with their letters and sentences, so it doubles as a legend like the "Define:" lists of textbook exercises (see `Docs/Palette.md`).
- `ABlock` keeps its token, so the formula's blocks can be turned back into tokens, for Undo and later for the tree (see `Docs/Logic.md`), and a palette item can report the token it inserts. It also builds its state on request (`FBlockState`, in `BlockData.h`): the base fills in the token and a subclass adds what is its own, through `GetState` and `ApplyState`, as with `GetText`; `APropositionBlock` adds whether it is minimized (see `Docs/Commands.md`). The state is built on request rather than kept in the base, since only propositions minimize.
- The notation (`FNotation`) holds what the player sees, and the levels never depend on it. The letters are a run of consecutive letters from a given first one: index N gets the letter N places after the first, with a `check` that the result is still a letter. Operator texts are kept by kind, from one of two symbol styles (`ESymbolStyle`), passed to the constructor like the first letter: the textbook symbols (∧, ∨, ↔...) or ASCII texts. Until the player chooses them (4.1), every factory builds its notation with the defaults kept in `FNotation` (P and the textbook symbols), so the formula and the palettes show the same letters and symbols. The blocks' font must hold every symbol (see `Docs/Font.md`).
- The textbook symbols are written in the code as their Unicode code points, in an array of numbers, and turned into text with `FString::Chr`. `TEXT` cannot take them from a variable, since it is a macro that only marks a literal; and the source stays ASCII, which avoids encoding problems and symbols that the IDE's font may not show.
- The notation lives in `Gameplay/Notation/`, not in `Logic/`: it uses engine types, and the core never needs it, since validity and equivalence do not depend on how a formula is shown. The analyzer has its own notation, the fixed one levels are written in (see `Docs/Levels.md`). The name is the logic term for how formulas are written; in Unreal, "Style" names the look of widgets (`FButtonStyle`).
- Shared types are grouped by domain (`Logic/LogicTypes.h`), not by kind of type.
- Rejected: global `Structs`/`Enumerators` files in a `SharedData` folder (unrelated types side by side, included everywhere); a factory holding block classes set in the Details panel (Blueprint subclasses that only held the material; see `Docs/Data.md`); text handling moved down to the subclasses (it would open `Label` and `Background` to them, or duplicate them in each); the base keeping the text, with one method to store it before construction and another to show it later (two paths for the same text); a `SetText` overridden in `APropositionBlock` (it was not virtual, and the name would lie, since the block may show the letter); one appearance method shared by `OnConstruction` and the subclasses that also notifies the listener (during construction the block has no listener yet); separate setters for the letter and the sentence (both always come together, once, at creation, so one method plays the part of the constructor an actor cannot have); a list of letters in each notation (computing them makes a notation just its first letter, at the cost of allowing only runs of consecutive letters); the notation in `AExercise`, which would get the letter or the text before calling the factory (it would repeat the factory's decision of which block gets which); the notation passed to a static factory on every call (it crossed every signature); `T` and `F` for the constants (`T` is also a letter) and `^` for XOR (many read it as AND); the textbook symbols typed in the source (non-ASCII text, which the compiler may read with the wrong encoding); one named variable per symbol, each set with `TEXT` (every symbol written twice, in its variable and in the array); the factory reading a proposition's number from a token's text (two classes would know the level format); a single call that analyzes the level's text and creates the blocks (it would hide the tokens of the starting formula, which the equivalence indicator needs); the factory taking the analyzer's `std::vector` (standard types would spread into the gameplay code, while the bridge converts them once); one class that takes the level row and does everything, from the text to the blocks (it would mix the logic core with the creation of actors); the stub creating its blocks itself (a second copy of the factory, to keep up with every change to the blocks); a stub that returns a level row (the stub stands in for the analyzer, not for the table); separate setters for the height and the token (both always come together, once, at creation, like the letter and the sentence); the stub's swap where the blocks are created rather than where the level is read (Undo would mix the stub's tokens with the level's sentences); one factory held by `AExercise` and shared by the formula and the palettes (the problem's level would handle actors and the blocks' height, while the defaults in `FNotation` already make every factory show the same symbols); the notation's first letter and symbol style chosen by `AExercise` (the notation is the player's choice, not the level's); the sentences passed to each request that creates blocks (the operator palette built an empty list, while whoever keeps the factory can keep them); separate requests to create a block and to place it (a block could be left off the board, outside the rows, where neither Restart nor Undo would destroy it); the factory built in the board's constructor with a placeholder height, replaced in `SetData` (a factory in an invalid state until then, while the `TOptional` says that it does not exist yet).
