# Level result design

The rule is in Game design, in `CLAUDE.md`. This file holds its details and reasons, and the alternatives rejected.

- The player ends a level by submitting the formula, with the panel's Submit button, and the game checks the formula only then, never after each change. As in a course's exercise, the player decides when the formula is the simplest, and the game does almost nothing for the player (see Game design in `CLAUDE.md`).
- Submit is enabled only while the formula is equivalent to the level's solution, when the equivalence indicator shows ≡ (see `Docs/Indicators.md`), so a submitted formula is always correct. The exercise reports the equivalence through an event that the GameMode connects to the panel, as it connects the formula's selection (see `Docs/Assembly.md`). The starting formula is equivalent, so the button starts enabled.
- A submitted formula wins when it has the solution's size: the number of leaves of its tree, its propositions and constants (see `Docs/Logic.md`). The level's author gives the smallest formula as the solution (see `Docs/Levels.md`), so a formula of that size is as simple as it gets. Anything else loses, an early submission included, even right at the start, unless the starting formula is already the simplest.
- A defeat costs the level's progress: after the result screen's OK, the level restarts through the same Restart as the panel's button, which clears the undo history, so Undo cannot bring the submitted formula back (see `Docs/Commands.md`). Without a cost, the player could submit after every change and let the game say when to stop.
- The exercise decides the result: it keeps whether the formula is solved (`bIsSolved`), computed after every change together with the indicators' answers, and `Submit` only reports it, through an event that the GameMode connects to the result screen (see `Docs/Exercise.md`).
- The result screen, `UResultScreen`, is a UMG widget like the panel: a C++ class with the logic and a Widget Blueprint, `WBP_ResultScreen`, with the layout (see `Docs/Data.md`). The GameMode creates it after the panel, and it starts hidden (Collapsed, which also takes it out of the layout and of the presses). It shows itself when the exercise reports a submission: a box in the middle of the screen, with the message and an OK button. The submitted formula stays on the table until the OK, so the player sees what won or what failed.
- The OK hides the screen and reports the result it showed, through a single event with a bool, which the GameMode binds to its own method: after a defeat, the GameMode calls the exercise's Restart; after a victory, it opens the next level. For that, the GameMode keeps the exercise in a field. A Restart from the panel shows no screen, since it is the player's own decision.
- The next level opens by reopening the map, `Main`, with `UGameplayStatics::OpenLevel`, and the next level's index in the travel options (`LevelIndex=1`). The engine destroys the old world and creates a new one, whose GameMode reads the index from its `OptionsString` and assembles the table as on the first run, where the option is missing and the index is 0 (see `Docs/Assembly.md`). No piece of the table needs to reset itself, and a short pause between levels is acceptable. After the last level, the index goes back to 0.
- The messages are short, in two lines: "Congratulations!" and "You solved it!" for a victory, or "Congratulations!" and "All levels solved!" after the last level, which the GameMode tells the screen when it creates it; "Not simple enough!" and "Try again?" for a defeat, which says what failed, since a submitted formula is always equivalent. They are defaults in the code (see Data rules in `CLAUDE.md`).
- The box's outline and the OK button's take the result's color, set in code: cyan (#22D3EE), the indicators' yes, for a victory, and bright red (#FF0000) for a defeat, brighter than the indicators' red, for more drama. The Widget Blueprint keeps the shapes, the sizes and the outlines' widths (see `Docs/Visuals.md`).
- While shown, the screen takes every press, on the world and on the panel. A user widget is not hit-testable itself by default (Not Hit-Testable (Self Only)), only its children are; the screen becomes Visible when it shows, so the whole screen takes the presses, and it handles the mouse down and the double click (`FReply::Handled()`), so they stop there instead of reaching the game. A Border or an Image set to Visible is not enough, since a press that no widget handles goes on to the game; handling the double click is a precaution, not confirmed. The screen is above the panel in the viewport (Z-order 1, against the panel's 0), so it also covers the panel's buttons (see `Docs/Input.md`). Sources: [Can UMG borders/images block clickthrough into the game world?](https://answers.unrealengine.com/questions/307828/view.html); [user widgets are Self Hit Test Invisible by default](https://answers.unrealengine.com/questions/122518/view.html).
- Rejected: checking the formula after every change, with no Submit (the game would decide for the player when the formula is the simplest); submitting with no penalty (the player could submit after every change); the result as a message in the panel, with no button and no blocking (the panel would mix commands and results, and the level would restart before the player saw the submitted formula); the screen as an actor in the world, a subclass of `AAbstractBlocksManager` with a proposition as the OK button (a proposition shows its letter, as in "P: OK", in the propositions' yellow, so the button would be a proposition that is not one, and the message has no token either), with ⊤ as the button (a real token, but the author preferred UMG's button), or made of backgrounds and labels, as the indicators are (more layout code for what UMG already does); ✔ as a token kind, for the button (it is no piece of a formula, so the core would have a kind that no formula contains, and the notation would hold an interface mark, which `Docs/Indicators.md` keeps out of it); the whole screen as the button, "Tap to continue" (the author preferred an OK button); a collider in the world to block the presses (UMG takes the presses before the world, so the panel's buttons would stay active); a box covering the whole table (the author preferred a box in the game's style, while the blocking covers the whole screen anyway, unseen); the box at the top of the screen, over the proposition palette, to leave the formula visible (the author preferred the middle, covering part of the formula); a box that fits its content (too small for an alert, which should look like a Windows alert box); the result's color on the message (the author preferred the outlines); "Wrong!" for a defeat (the submitted formula is correct, only not the simplest); rebuilding the table in place for the next level, with the exercise, the formula and the proposition palette taking the new level's texts (each piece would need to reset itself, and the GameMode would keep acting after the assembly, while reopening the map leaves every piece as it is); keeping the level's index in the `UGameInstance`, the engine object that lives across maps (a global place where pieces look things up, while the travel options carry the index to the next map's GameMode); two events on the screen, one for a defeat, bound to the exercise's Restart, and one for a victory, bound to the GameMode (the GameMode would not keep the exercise, but the author preferred a single event with the result); a separate screen or map for the end of the game (a third message on the result screen is enough).
